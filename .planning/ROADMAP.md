**Granularity decision:** Honoring research recommendation of **3 coarse-grained phases** (SUMMARY.md §7) over the default `standard` (5-8). Splitting Phase 2 into separate Monetization vs Compliance phases would force LGPD endpoints to ship after checkout — but ANPD requires them BEFORE the first paid signup; they have to land together. Plan-level granularity inside each phase remains "standard" (5-8 plans per phase).

## Overview

MilesPro is a brownfield codebase (~1,285 commits, 6 months) that is technically functional but cannot accept a single paying customer in its current state. Three CRITICAL findings (`PITFALLS.md` CRIT-01/02 + `CONCERNS.md`) already manifest in code: client-only plan gating, service-role key referenced in `VITE_*` env, and a 5-vs-3 plan-enum mismatch held together by accident. The roadmap is therefore goal-backward from "user paid recurringly and we know it":

1. **Phase 1 — Security & Foundation Hardening** closes the gates so a Free user with their JWT cannot read or write paid data via direct REST. Trust kernel + RLS rewrite + secret hygiene + enum consolidation + critical-path test coverage. Nothing in Phase 2 can ship safely without this.
2. **Phase 2 — Monetização, Compliance & Telemetria** wires the Asaas pipeline (checkout, idempotent webhook, reconciliation), defines and enforces the Free/Pro/VIP feature matrix, ships LGPD DSR endpoints + consent + privacy/terms (legally required before first paid signup), turns on real PostHog + Sentry, and stands up the production web build, landing page and helpdesk. Asaas onboarding requires a CNPJ — see Phase 2 prerequisite block.
3. **Phase 3 — Mobile Distribution & Launch** ships the iOS Path C build (no IAP, no in-app pricing UI), Android with `targetSdk=35`, Universal/App Links, push notifications, App Review submission, and runs the first-10-pagantes outreach until LAUNCH-06 closes.

Each phase ends with curl/test-level acceptance, not status-check acceptance.

### Phase 1: Security & Foundation Hardening

**Goal**: A Free user authenticated with their own JWT cannot access paid data, the production bundle ships zero secrets, the plan enum is canonical and consolidated, and the four most security-sensitive untested code paths now have adversarial test coverage. This phase delivers the trust kernel that every subsequent paid feature delegates to.

**Depends on**: Nothing (first phase). All work is on the existing brownfield codebase.

**Requirements**: SEC-01, SEC-02, SEC-03, SEC-04, SEC-05, SEC-06, SEC-07

**Success Criteria** (what must be TRUE):
  1. **Adversarial RLS curl test passes:** A Free user's JWT used in `curl -X POST https://<project>.supabase.co/rest/v1/travel_cruises -H "Authorization: Bearer <jwt>" -d '{"user_id":"<own-uid>",...}'` returns HTTP 401/403.   1. **iOS build is App-Store-approved with a verifiable absence of in-app navigation to checkout:** Reviewer-installed build of `MilesPro.ipa` contains zero clickable links or programmatic navigations routing to checkout from inside iOS. Verified by CI gate `scripts/check-ios-strings.sh` running `grep -E 'href=["'"'"']/(planos|checkout|assinatura)|window\.location\.(href|assign|replace)\s*[=(]\s*["'"'"'][^"'"'"']*(planos|checkout|assinatura|asaas)|Browser\.open'` against `dist/assets/*.js` and returning zero matches, AND by manual UI walkthrough in TestFlight confirming no pricing/upgrade UI surfaces, no "Upgrade"/"Assinar" buttons, no path leading the user out of the app to web checkout. App Store Connect status reads "Ready for Sale" with no open rejections referencing 3.1.1 or 3.1.3.

     *Rationale for narrowed grep pattern (decided 2026-05-14 plan-phase 3 revision; refined 2026-05-14 plan-03-02 execution):* The original verbatim regex (`planos|checkout|R\$|Upgrade|Assinar`) cannot pass on a Vite-bundled SPA — the strings exist in shared React components gated at runtime by `useIsIOSCapacitor()`, not removed from the JS bundle. Apple's 3.1.3(b) Multiplatform Services rule cares about user-visible **navigation to** external purchase, not about cosmetic strings in a minified bundle. The narrowed pattern catches every realistic Path C anti-pattern (anchor tags, programmatic `window.location` redirects, `Browser.open` calls) while remaining a green CI signal. The TestFlight walkthrough is the user-visible-UI gate; this grep is the code-path defense in depth.

     *Refinement (2026-05-14 — plan-03-02 execution):* The original narrowed pattern `window\.location.*(?:planos|checkout|assinatura)` was greedy: `.*` matches across the entire minified-line bundle, conflating reads (`window.location.pathname`) with writes, and producing 200KB single-line matches that drown the signal. The refined pattern requires (a) `window.location.(href|assign|replace)` followed by `=` or `(` (write semantics — distinguishes assignment from `pathname`/`search`/`hash` reads), AND (b) a literal string argument containing one of the pricing tokens (so a generic `window.location.href = data.auth_url` for OAuth does not trigger). The literal-URL constraint means variable-URL writes (e.g., `window.location.href = checkoutUrl` inside `handlePlanCta`) are NOT caught by the bundle gate — those are defended by (i) the per-component `useIsIOSCapacitor()` wrap (Plan 02-06 / 03-02 Task 4 unit tests prove the component renders nothing on iOS, so the handler never executes) and (ii) the TestFlight manual walkthrough. Net effect: precise gate that catches new literal-pricing-route writes (developer regression vector), and full-component Path C wrap defends variable-URL handlers.
